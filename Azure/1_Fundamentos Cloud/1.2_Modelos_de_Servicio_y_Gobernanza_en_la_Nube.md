## 1. Taxonomía IaaS, PaaS y SaaS

### 1.1 La idea central: nivel de abstracción y control

Los tres modelos representan **puntos distintos en un mismo espectro**: cuánta infraestructura administra el cliente versus cuánta administra el proveedor de la nube (Azure). A medida que se avanza de IaaS → PaaS → SaaS, el cliente **cede control técnico** a cambio de **menos trabajo operativo**.

```
Más control / más trabajo del cliente ────────────────► Menos control / menos trabajo del cliente

   On-Premises        IaaS              PaaS                SaaS
  (todo lo admin.   (Azure admin.   (Azure admin.       (Azure admin.
   el cliente)       el hardware     además el SO,       todo, incluida
                      físico y la    runtime, parches     la aplicación;
                      red física)    y backups del        el cliente solo
                                     motor)                la usa)
```

### 1.2 Infrastructure as a Service (IaaS)

**Definición:** Azure entrega la **infraestructura** (servidores virtuales, redes, almacenamiento) y el **cliente administra el sistema operativo** hacia arriba: instalación de parches del SO, configuración del runtime, middleware, y la aplicación misma.

- **Ejemplo típico:** Azure Virtual Machines (VMs), Azure Virtual Network, Managed Disks.
- **Qué administra el cliente:** sistema operativo, parches del SO, runtime, middleware, datos, aplicación, configuración de red interna de la VM.
- **Qué administra Azure:** virtualización, servidores físicos, almacenamiento físico, redes físicas, centros de datos.
- **Cuándo se usa:** cuando se necesita **control total** sobre el entorno (ej. migraciones "lift-and-shift" de aplicaciones legacy, software que requiere configuraciones específicas del SO).

### 1.3 Platform as a Service (PaaS)

**Definición:** Azure **abstrae la infraestructura completa**, incluyendo el sistema operativo, y **delega a Azure la aplicación de parches, backups, alta disponibilidad y el motor de ejecución**. El cliente se enfoca únicamente en su aplicación y sus datos.

- **Ejemplo típico (clave para el examen):** **Azure SQL Database** — Azure administra el motor de base de datos, aplica parches automáticamente y realiza backups automáticos; el cliente solo diseña el esquema, escribe las consultas y administra los datos.
- Otros ejemplos: Azure App Service, Azure Functions, Azure Data Factory, Azure Synapse Analytics (en su capa de servicio administrado).
- **Qué administra el cliente:** datos, aplicación/lógica de negocio, configuración de la app.
- **Qué administra Azure:** sistema operativo, runtime, parches, backups, escalado de infraestructura subyacente, alta disponibilidad del motor.
- **Cuándo se usa:** cuando se quiere **reducir la carga operativa** (no administrar SO ni backups) y enfocarse en el desarrollo de la aplicación o en el análisis de datos.

### 1.4 Software as a Service (SaaS)

**Definición:** Azure (o el proveedor del software) entrega el **producto final, listo para usar**, accesible normalmente vía navegador o app, sin que el cliente administre absolutamente nada de la infraestructura o la plataforma subyacente.

- **Ejemplo típico:** Microsoft 365, Dynamics 365, Power BI Service (como producto SaaS de consumo final).
- **Qué administra el cliente:** únicamente la configuración de uso de la aplicación y sus datos dentro de ella (usuarios, permisos de negocio, contenido).
- **Qué administra el proveedor:** todo lo demás — infraestructura, plataforma, la aplicación en sí, sus actualizaciones.

### 1.5 Cuadro comparativo (alto valor en examen)

| Capa administrada por... | IaaS | PaaS | SaaS |
|---|---|---|---|
| Datos | Cliente | Cliente | Cliente |
| Aplicaciones | Cliente | Cliente | Proveedor |
| Runtime | Cliente | **Proveedor** | Proveedor |
| Middleware | Cliente | Proveedor | Proveedor |
| Sistema Operativo | Cliente | Proveedor | Proveedor |
| Virtualización | Proveedor | Proveedor | Proveedor |
| Servidores físicos | Proveedor | Proveedor | Proveedor |
| Almacenamiento físico | Proveedor | Proveedor | Proveedor |
| Redes físicas | Proveedor | Proveedor | Proveedor |

> **Frase clave para examen:** *"El nivel de responsabilidad que el cliente administra: IaaS deja más control (y trabajo) al cliente; PaaS abstrae la infraestructura; SaaS entrega la aplicación completa lista para usar."*

### 1.6 Errores comunes / distractores típicos del balotario

- ❌ "No hay ninguna diferencia real, son sinónimos" → **Falso**, cada uno tiene un límite de responsabilidad distinto.
- ❌ "IaaS es siempre más barato que PaaS y SaaS" → **Falso**, el costo depende del caso de uso, no del modelo en sí.
- ❌ "SaaS solo aplica a bases de datos" → **Falso**, SaaS es cualquier software completo entregado como servicio (ej. Office 365).
- ❌ "PaaS requiere administrar servidores físicos" → **Falso**, esa es precisamente la capa que PaaS abstrae.
- ❌ Confundir Azure SQL Database (**PaaS**) con una VM con SQL Server instalado manualmente (**IaaS**) — la diferencia está en quién aplica los parches y backups del motor.

## 2. Modelo de Responsabilidad Compartida (Shared Responsibility Model)

### 2.1 Definición

El **Shared Responsibility Model** es el **marco de cumplimiento (compliance)** que define **qué gestiona Microsoft** y **qué gestiona el cliente** en un entorno de nube. No es un concepto de "todo o nada": la línea divisoria **se desplaza según el modelo de servicio contratado** (IaaS, PaaS o SaaS) — a más abstracción (SaaS), más responsabilidad asume Microsoft; a menos abstracción (IaaS), más responsabilidad asume el cliente.

> **Definición para examen (memorizar):** *"Un marco que define qué aspectos de seguridad y cumplimiento gestiona el proveedor de la nube (Azure) y cuáles corresponden al cliente, variando según el modelo IaaS, PaaS o SaaS."*

### 2.2 Lo que Microsoft siempre gestiona (en cualquier modelo)

Independientemente de si el servicio es IaaS, PaaS o SaaS, Microsoft **siempre** es responsable de:

- **Seguridad física de los centros de datos** (control de acceso físico, energía, refrigeración).
- **Infraestructura de red física** y de la nube global.
- **Capa de virtualización** (hipervisor).

### 2.3 Lo que el cliente siempre gestiona (en cualquier modelo)

Sin importar el modelo de servicio, el cliente **nunca deja de ser responsable** de:

- **Datos** (clasificación, protección, cifrado a nivel de aplicación si aplica).
- **Endpoints** (dispositivos desde los que se accede).
- **Cuentas e identidades** (gestión de usuarios, credenciales, políticas de acceso — Microsoft provee la herramienta como Microsoft Entra ID, pero el cliente decide cómo configurarla y quién tiene acceso).

> **Idea clave para examen:** *"Datos, endpoints e identidades son responsabilidad del cliente en **todos** los modelos — incluso en SaaS."* Este es un punto que el balotario suele usar como trampa: aunque SaaS delega casi todo a Microsoft, la seguridad de las **cuentas de usuario** y la **clasificación de los datos** siguen siendo del cliente.

### 2.4 Cómo se desplaza la responsabilidad según el modelo

| Área de responsabilidad | On-Premises | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| Datos, clasificación y protección | Cliente | Cliente | Cliente | Cliente |
| Identidades y dispositivos (endpoints) | Cliente | Cliente | Cliente | Cliente |
| Aplicación | Cliente | Cliente | Cliente | **Microsoft** |
| Sistema operativo | Cliente | Cliente | **Microsoft** | Microsoft |
| Infraestructura de red (configuración lógica) | Cliente | Cliente / Compartida | Microsoft | Microsoft |
| Servidores físicos, hosts | Cliente | **Microsoft** | Microsoft | Microsoft |
| Centro de datos físico | Cliente | Microsoft | Microsoft | Microsoft |

*(En negrita, el punto donde "cruza" la responsabilidad de cliente a Microsoft en cada modelo respecto al anterior.)*

### 2.5 Por qué es un "marco de cumplimiento"

Se le llama marco de **compliance** porque en auditorías de seguridad (ISO 27001, SOC 2, normativas locales de protección de datos) es necesario **demostrar exactamente quién es responsable de qué control**. El Shared Responsibility Model es el documento de referencia que Microsoft publica para que las organizaciones sepan qué controles de seguridad deben implementar ellas mismas y cuáles ya están cubiertos por Azure.

### 2.6 Errores comunes / distractores típicos del balotario

- ❌ "Un acuerdo donde el cliente es responsable de absolutamente todo" → **Falso**, es precisamente un modelo **compartido**.
- ❌ "Un modelo exclusivo para facturación compartida entre departamentos" → **Falso**, no tiene relación con billing interno, es sobre seguridad y cumplimiento.
- ❌ "Solo aplica a servicios de almacenamiento" → **Falso**, aplica a **todos** los servicios de Azure sin excepción.
- ❌ Pensar que en SaaS el cliente **no tiene ninguna responsabilidad** → **Falso**, siempre conserva datos, endpoints e identidades.

## 3. Relación entre ambos conceptos (IaaS/PaaS/SaaS + Shared Responsibility)

Estos dos temas del punto 1.2 están **directamente conectados**: la taxonomía IaaS/PaaS/SaaS define **el nivel de abstracción técnica**, y el Shared Responsibility Model define **quién asume la seguridad y el cumplimiento** en cada uno de esos niveles. Una forma de recordarlo:

> *"El modelo de servicio (IaaS/PaaS/SaaS) determina **dónde termina la responsabilidad técnica de Azure**; el Modelo de Responsabilidad Compartida es la traducción de ese límite técnico en términos de **seguridad y cumplimiento**."*

## 5. Tips finales para el examen sobre este punto

1. Si la pregunta menciona **"quién administra el sistema operativo"** → distingue: IaaS = cliente, PaaS/SaaS = Microsoft.
2. Si menciona **"Azure administra parches y backups del motor"** → es el ejemplo de **PaaS** (Azure SQL Database es el caso de referencia del balotario).
3. Si la pregunta habla de **"seguridad física del centro de datos"** → siempre es responsabilidad de **Microsoft**, en cualquier modelo.
4. Si la pregunta habla de **"datos, endpoints o identidades"** → siempre es responsabilidad del **cliente**, incluso en SaaS.
5. No caigas en la trampa de pensar que un modelo "más abstracto" (SaaS) libera al cliente de **toda** responsabilidad — nunca es así.
6. Relaciona siempre "modelo de servicio" (técnico) con "modelo de responsabilidad compartida" (seguridad/cumplimiento) — son dos caras de la misma idea.
