## 1. Availability Zones (Zonas de Disponibilidad)

### 1.1 Definición

Las **Availability Zones (Zonas de Disponibilidad)** son la **protección contra desastres a nivel de centro de datos**. Son **ubicaciones físicas separadas** dentro de una **misma región** de Azure, cada una equipada con **energía, refrigeración y red independientes**, diseñadas para garantizar **tolerancia a fallos**: si una zona falla (por un corte eléctrico, incendio, falla de red), las otras zonas siguen operando con normalidad.

> **Definición para examen (memorizar):** *"Una Availability Zone es una ubicación física separada dentro de una región de Azure, con energía y refrigeración independientes, para tolerancia a fallos."*

### 1.2 Dónde encajan en la jerarquía de resiliencia geográfica de Azure

Azure organiza su infraestructura física en varios niveles, cada uno protegiendo contra un tipo distinto de falla:

```
Geography (Geografía)          ← ej. "Estados Unidos", conjunto de regiones para soberanía de datos
   └── Region (Región)         ← ej. "East US", conjunto de datacenters con baja latencia entre sí
        └── Availability Zone  ← ubicación física separada dentro de la región (energía/red propia)
             └── Datacenter(s) ← uno o más centros de datos físicos dentro de cada zona
```

- Una **región** típica que soporta Availability Zones tiene **como mínimo 3 zonas separadas**.
- Cada zona está lo suficientemente **cerca** de las demás (dentro de la misma región) para tener **latencia de red baja** entre ellas, pero lo suficientemente **lejos físicamente** para no compartir el mismo punto único de falla (energía, refrigeración, conectividad de red).

### 1.3 Qué protegen las Availability Zones (y qué no)

| Escenario de falla | ¿Lo cubre una Availability Zone? |
|---|---|
| Corte eléctrico en un datacenter específico | ✅ Sí — las otras zonas tienen energía independiente |
| Falla de refrigeración en un datacenter | ✅ Sí — cada zona tiene refrigeración independiente |
| Falla de red interna de una zona | ✅ Sí — cada zona tiene conectividad de red independiente |
| Desastre que afecta a **toda la región** (ej. un desastre natural regional) | ❌ No — para esto se necesita **replicación geográfica entre regiones distintas** (geo-redundancia), no solo zonas |

> **Idea clave para examen:** las Availability Zones protegen contra fallas **dentro de una región** (a nivel de datacenter). Para protección ante la **pérdida de una región completa**, se necesita una estrategia de **múltiples regiones** (fuera del alcance de este punto, pero relevante para Disaster Recovery).

### 1.4 Cómo se usan en la práctica

- **Recursos zone-redundant:** algunos servicios de Azure (VMs con conjuntos de escalado zonales, Azure SQL Database con zone redundancy, Storage con Zone-Redundant Storage — ZRS) pueden desplegarse **replicando automáticamente entre varias zonas** de la misma región, logrando alta disponibilidad sin necesidad de gestionar manualmente la replicación.
- **Recursos zonal (pinned a una zona):** también es posible anclar explícitamente un recurso (por ejemplo, una VM) a una zona específica, útil cuando se quiere control manual sobre en qué zona vive cada réplica de una arquitectura de alta disponibilidad diseñada por el cliente.
- No todas las regiones de Azure soportan Availability Zones — es importante verificar la disponibilidad de zonas antes de diseñar una arquitectura que dependa de ellas.

### 1.5 Errores comunes / distractores típicos del balotario

- ❌ "Un tipo de suscripción gratuita" → **Falso**, no tiene relación con planes de facturación.
- ❌ "Un grupo de recursos con permisos restringidos" → **Falso**, eso describe (mal) un Resource Group con RBAC, no una Availability Zone.
- ❌ "Un servicio de red exclusivo para IoT" → **Falso**, las Availability Zones aplican a infraestructura física general, no a un servicio específico.
- ❌ "Una zona horaria configurada por el usuario" → **Falso**, "zona" aquí se refiere a ubicación física del datacenter, no a huso horario.
- ⚠️ No confundir **Availability Zone** (dentro de una región) con **Region** (geográficamente distinta, potencialmente en otro país/continente) — son conceptos de distinto nivel en la jerarquía.

## 2. Dinámica de Escalado: Scale Up vs. Scale Out

### 2.1 Los dos ejes del escalado en la nube

Cuando un recurso necesita más capacidad, hay **dos estrategias distintas** para lograrlo, y el balotario suele pedir distinguirlas con precisión:

| | **Scale Up (Escalado Vertical)** | **Scale Out (Escalado Horizontal)** |
|---|---|---|
| **Qué hace** | Aumenta la capacidad (CPU, memoria, disco) de **una instancia existente** | Agrega **más instancias idénticas** del mismo recurso |
| **Ejemplo** | Cambiar una VM de tamaño `Standard_D2s` a `Standard_D8s` (más vCPUs y RAM) | Pasar de 2 a 5 instancias de una VM detrás de un Load Balancer, o aumentar las unidades de un App Service Plan |
| **Límite** | Tiene un techo — eventualmente no existe una instancia "más grande" disponible | Prácticamente ilimitado — se pueden seguir agregando instancias |
| **Downtime típico** | Puede requerir reinicio del recurso (dependiendo del servicio) | Generalmente no requiere downtime — las nuevas instancias se suman al pool |
| **Analogía** | "Conseguir un empleado más fuerte y capaz" | "Contratar más empleados para repartir el trabajo" |

### 2.2 Definición de Scale Up (Escalado Vertical) — foco del temario

> **Definición para examen (memorizar):** *"Escalado vertical (Scale Up): consiste en aumentar la capacidad de cómputo (CPU, memoria) de una instancia de recurso existente, a diferencia del escalado horizontal (scale out) que añade más instancias idénticas."*

- Se aplica típicamente a: **Virtual Machines** (cambiar el tamaño/SKU de la VM), **Azure SQL Database** (subir de tier de servicio, ej. de `Standard` a `Premium`, o aumentar DTUs/vCores), **App Service Plans** (subir de tier).
- **Scale down** es la operación inversa: reducir la capacidad de la instancia existente (para ahorrar costos en horarios de baja demanda).

### 2.3 Definición de Scale Out (Escalado Horizontal) — para contraste

- Consiste en **añadir más instancias idénticas** del recurso para repartir la carga entre ellas, en lugar de hacer más grande una sola instancia.
- Ejemplos: **Virtual Machine Scale Sets (VMSS)** que agregan/quitan VMs automáticamente según demanda; **App Service** con múltiples instancias detrás de un balanceador; particiones adicionales en un sistema distribuido.
- **Scale in** es la operación inversa: quitar instancias cuando la demanda baja.
- Suele combinarse con **autoescalado (autoscaling)**: reglas automáticas basadas en métricas (CPU %, longitud de cola, etc.) que agregan o quitan instancias sin intervención manual.

### 2.4 Por qué la distinción importa en un examen de Data Engineer

- Motores de datos distribuidos (Synapse Dedicated SQL Pool, Databricks, Spark) suelen escalar **horizontalmente** (más nodos de cómputo) para paralelizar el procesamiento de grandes volúmenes.
- Una sola base de datos transaccional (Azure SQL Database en configuración estándar) suele escalar primero **verticalmente** (subir de tier) antes de considerar particionamiento u otras estrategias horizontales.
- Entender esta diferencia ayuda a elegir la estrategia correcta de optimización de costos y rendimiento según el tipo de carga de trabajo (OLTP vs. analítica masiva).

### 2.5 Errores comunes / distractores típicos del balotario

- ❌ "Agregar más instancias del mismo recurso" como definición de escalado vertical → **Falso**, esa es la definición de **escalado horizontal (scale out)**, no de scale up.
- ❌ "Mover el recurso a otra región" → **Falso**, no tiene relación con escalado, es una operación de migración/geolocalización.
- ❌ "Eliminar recursos no utilizados" → **Falso**, eso es optimización de costos, no escalado.
- ❌ "Cambiar el proveedor de nube" → **Falso**, no tiene relación con el concepto.

## 3. Cuadro resumen para memorizar (alto valor en examen)

| Concepto | Definición corta |
|---|---|
| **Availability Zone** | Ubicación física separada dentro de una región, con energía/refrigeración/red independientes, para tolerancia a fallos a nivel de datacenter. |
| **Region** | Conjunto de datacenters (potencialmente organizados en zonas) en una ubicación geográfica; nivel superior a la Availability Zone. |
| **Zone-redundant** | Un recurso que replica automáticamente entre varias Availability Zones de una misma región. |
| **Scale Up (vertical)** | Aumentar la capacidad (CPU/RAM) de **una** instancia existente. |
| **Scale Down** | Operación inversa a Scale Up: reducir la capacidad de la instancia existente. |
| **Scale Out (horizontal)** | Añadir **más instancias idénticas** para repartir la carga. |
| **Scale In** | Operación inversa a Scale Out: quitar instancias. |
| **Autoscaling** | Reglas automáticas que ajustan el número de instancias (scale out/in) según métricas de demanda. |

## 5. Tips finales para el examen sobre este punto

1. Si la pregunta menciona **"ubicación física separada", "energía y refrigeración independientes", "dentro de una misma región"** → es **Availability Zone**.
2. Si la pregunta menciona **"aumentar CPU/memoria de una instancia existente"** → es **Scale Up (vertical)**.
3. Si la pregunta menciona **"agregar más instancias idénticas"** → es **Scale Out (horizontal)**, el opuesto de scale up — no los confundas.
4. Recuerda la jerarquía: **Geography → Region → Availability Zone → Datacenter**.
5. Las Availability Zones protegen contra fallas **dentro de una región** (a nivel de datacenter), **no** contra la pérdida de una región completa — eso requiere multi-región.
6. Asocia mentalmente: **"Zone" = resiliencia física (disponibilidad)**; **"Scale" = capacidad de cómputo (rendimiento/costo)** — son dos problemas distintos que el examen puede mezclar en la misma pregunta.
