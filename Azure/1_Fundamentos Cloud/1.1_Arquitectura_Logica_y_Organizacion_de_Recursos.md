# 1.1 Arquitectura Lógica y Organización de Recursos (Azure)

> Manual de estudio detallado — preparación para el Balotario Azure Cloud (GDN-e Perú · Chapter Data).
> Cubre exclusivamente el punto **1.1** del temario: jerarquía de organización de recursos, Resource Groups, y la capa de aislamiento/gobernanza (RBAC + Azure Policy).

---

## 1. La jerarquía de organización de Azure

Antes de entender qué es un Resource Group hay que ver **dónde vive** dentro de la estructura completa de Azure. Esta jerarquía es la base sobre la que se aplican permisos (RBAC) y políticas (Azure Policy), y es un tema clásico de examen porque las preguntas suelen pedir "¿en qué nivel se puede aplicar X?".

```
Tenant (Microsoft Entra ID / Azure AD)
 └── Management Group(s)          ← agrupa varias suscripciones
      └── Subscription(s)         ← límite de facturación y de cuotas técnicas
           └── Resource Group(s)  ← contenedor lógico de recursos relacionados
                └── Resource(s)   ← VM, Storage Account, SQL DB, ADF, etc.
```

**Reglas clave de la jerarquía:**

- Cada nivel es un **ámbito (scope)** válido para asignar roles RBAC o políticas de Azure Policy.
- Los permisos y políticas se **heredan hacia abajo**: lo que se asigna en un Management Group aplica a todas las suscripciones, grupos de recursos y recursos que contiene; lo asignado en una suscripción aplica a todos sus grupos de recursos, etc.
- Un **recurso** solo puede pertenecer a **un** Resource Group a la vez (pero se puede mover a otro).
- Un **Resource Group** pertenece a **una sola suscripción**.
- Los **Management Groups** existen para organizar múltiples suscripciones bajo una sola jerarquía de gobernanza (por ejemplo, separar "Producción" de "No Producción", o agrupar por unidad de negocio), típico en organizaciones grandes con múltiples suscripciones.

## 2. Resource Groups (Grupos de Recursos)

### 2.1 Definición

Un **Resource Group (RG)** es el **contenedor lógico fundamental** de Azure. Agrupa recursos relacionados (bases de datos, VNets, Data Factories, storage accounts, etc.) que comparten un mismo ciclo de vida, con el fin de:

1. **Administrarlos como una unidad** (desplegar, actualizar, eliminar todo junto).
2. **Monitorearlos** de forma conjunta (dashboards, alertas por RG).
3. **Facturarlos** como una unidad — Azure Cost Management permite ver el gasto agrupado por Resource Group.

> **Definición para examen (memorizar):** *"Un Resource Group es un contenedor lógico que agrupa recursos relacionados de Azure para administrarlos, monitorearlos y facturarlos juntos."*

### 2.2 Características técnicas importantes

| Característica | Detalle |
|---|---|
| **Ubicación (location) del RG** | El RG en sí tiene una región asociada (donde se guarda su metadata), pero **los recursos dentro pueden estar en regiones distintas** a la del RG. |
| **Pertenencia** | Un recurso vive en **un solo** RG a la vez. Se puede **mover** un recurso de un RG a otro (con algunas restricciones según el tipo de recurso). |
| **Eliminación en cascada** | Borrar un Resource Group **borra todos los recursos que contiene**. Es la forma más común de "limpiar" un entorno de pruebas completo con una sola acción. |
| **Nombres únicos** | El nombre del RG debe ser único **dentro de la suscripción**. |
| **No es un límite de red ni de seguridad por sí solo** | El RG organiza y gobierna, pero no aísla tráfico de red (eso lo hacen las VNets/NSGs) — sí puede ser el ámbito de un rol RBAC o de una política. |
| **Etiquetas (Tags)** | Se pueden aplicar tags a nivel de RG (y heredarlos conceptualmente para reportes), útiles para clasificar por proyecto, entorno (`dev`/`qa`/`prod`), centro de costos, dueño, etc. |
| **Locks (bloqueos)** | Se pueden aplicar **Resource Locks** a nivel de RG: `CanNotDelete` (evita borrado accidental) y `ReadOnly` (evita cualquier modificación). Se heredan a todos los recursos del grupo. |

### 2.3 ¿Por qué existen los Resource Groups?

- **Ciclo de vida compartido:** normalmente los recursos de una misma aplicación/solución (por ejemplo, un Data Factory + su Storage Account + su Key Vault) se crean y se destruyen juntos → van en el mismo RG.
- **Facturación granular:** un negocio puede tener un RG por proyecto o por equipo, y ver exactamente cuánto gasta cada uno.
- **Punto de aplicación de gobernanza:** es uno de los **cuatro ámbitos** (junto con Management Group, Suscripción y Recurso individual) donde se pueden aplicar **RBAC** y **Azure Policy** — ver sección 3.

### 2.4 Buenas prácticas típicas de examen

- Agrupar por **aplicación/solución** o por **ciclo de vida** (no por tipo de recurso).
- Usar una **convención de nombres** consistente (ej. `rg-<proyecto>-<entorno>-<region>`).
- Usar **tags obligatorias** (impuestas vía Azure Policy) para centro de costo, entorno, dueño.
- No mezclar recursos de **producción** y **no-producción** en el mismo RG.

## 3. Aislamiento y Gobernanza

La segunda mitad del punto 1.1 trata sobre **cómo se controla quién puede hacer qué, y qué configuraciones son válidas**, usando el Resource Group (o cualquier otro nivel de la jerarquía) como el ámbito donde se aplican estas reglas.

Hay **dos mecanismos de gobernanza distintos y complementarios** que el examen suele confundir a propósito en las opciones incorrectas — es crítico entender la diferencia:

| | **RBAC (Role-Based Access Control)** | **Azure Policy** |
|---|---|---|
| **Pregunta que responde** | ¿**Quién** puede hacer **qué** acción sobre un recurso? | ¿**Qué características/configuración** puede tener un recurso, sin importar quién lo creó? |
| **Controla** | Acceso y acciones (leer, escribir, eliminar, administrar permisos) | Cumplimiento (compliance): SKUs permitidos, regiones permitidas, tags obligatorios, cifrado obligatorio, etc. |
| **Se aplica a** | Usuarios, grupos, service principals, managed identities (identidades) | Recursos (independiente de quién los creó o los administra) |
| **Ejemplo** | "El equipo de Data Engineering puede leer y escribir en este RG, pero no eliminar recursos" | "Todo recurso creado en este RG debe estar en la región `East US` y debe tener la etiqueta `CostCenter`" |
| **Efecto típico** | Permite / deniega una acción | `Deny`, `Audit`, `Append`, `Modify`, `DeployIfNotExists`, `Disabled` |

> **Idea clave para el examen:** RBAC = permisos de **personas/identidades**. Azure Policy = reglas sobre **recursos**. Ambos se aplican sobre el mismo tipo de ámbitos (Management Group → Suscripción → Resource Group → Recurso), pero resuelven problemas distintos.

### 3.1 RBAC (Role-Based Access Control)

#### Definición

**RBAC** es el sistema de autorización de Azure que **otorga permisos a usuarios, grupos o aplicaciones** mediante **roles asignados** sobre un **ámbito** determinado (recurso, grupo de recursos, suscripción o management group).

> **Definición para examen (memorizar):** *"RBAC es un sistema que otorga permisos a usuarios, grupos o aplicaciones mediante roles asignados sobre un ámbito (recurso, grupo de recursos o suscripción)."*

#### Los tres componentes de una asignación de rol (Role Assignment)

Toda asignación RBAC se compone de **tres elementos**:

1. **Security Principal (¿Quién?)** — la identidad que recibe el permiso:
   - Usuario (persona)
   - Grupo (de Microsoft Entra ID / Azure AD)
   - **Service Principal** — identidad usada por **aplicaciones, servicios o pipelines de CI/CD** para autenticarse y actuar sobre recursos de Azure (no es una persona).
   - **Managed Identity** — identidad administrada automáticamente por Azure AD, asociada a un recurso (una Function App, una VM, un Data Factory), que permite autenticarse ante otros servicios **sin guardar credenciales/secretos en el código**. Es la alternativa moderna y recomendada frente a Service Principals con secretos manuales.

2. **Role Definition (¿Qué puede hacer?)** — la colección de permisos. Roles **integrados (built-in)** más comunes:
   - **Owner:** control total, incluida la capacidad de asignar permisos a otros.
   - **Contributor:** puede crear y administrar todos los recursos, **pero no puede otorgar acceso a otros** (no administra RBAC).
   - **Reader:** solo puede ver los recursos, sin modificarlos.
   - **User Access Administrator:** administra el acceso de otros usuarios a recursos de Azure (sin poder modificar los recursos en sí).
   - También existen roles específicos por servicio (ej. *Storage Blob Data Contributor*, *SQL DB Contributor*) y se pueden crear **roles personalizados (custom roles)** combinando permisos granulares (`Microsoft.Storage/...`, `Microsoft.Sql/...`, etc.).

3. **Scope (¿Dónde aplica?)** — el nivel de la jerarquía donde se asigna: Management Group, Suscripción, Resource Group o Recurso individual. El permiso **se hereda hacia los niveles inferiores** del ámbito elegido.

#### Modelo aditivo

El modelo de RBAC en Azure es **aditivo**: si a un usuario se le asignan dos roles distintos, sus permisos se **suman**. No existen "deny rules" tradicionales en RBAC estándar (las *Deny Assignments* solo existen en escenarios especiales como Azure Blueprints/Managed Applications, y tienen prioridad sobre cualquier permiso otorgado).

#### Principio de mínimo privilegio (Least Privilege)

Buena práctica y tema de examen (nivel avanzado): otorgar a **cada identidad** (usuario, service principal o managed identity) **únicamente los permisos estrictamente necesarios** para su función, en el **ámbito más reducido posible** (idealmente a nivel de Resource Group o incluso de recurso individual, no de suscripción completa), reduciendo la superficie de riesgo ante una credencial comprometida.

#### Autenticación vs. Autorización

Son conceptos distintos que suelen confundirse en el examen:

- **Autenticación (Authentication, AuthN):** verifica **quién eres** — el proceso de comprobar la identidad (login, MFA).
- **Autorización (Authorization, AuthZ):** determina **qué puedes hacer** una vez que ya fuiste autenticado — esto es exactamente lo que resuelve RBAC.

> La autenticación siempre ocurre **antes** que la autorización: primero se confirma la identidad (vía Microsoft Entra ID), luego RBAC decide qué acciones tiene permitidas esa identidad ya autenticada.

### 3.2 Azure Policy

#### Definición

**Azure Policy** es el servicio que permite **crear, asignar y hacer cumplir reglas de gobernanza** sobre los recursos de Azure — por ejemplo, exigir etiquetas obligatorias, restringir las regiones donde se pueden crear recursos, o limitar los tipos/SKU permitidos. A diferencia de RBAC, Azure Policy **no controla quién puede actuar**, sino **qué forma/configuración es válida** para un recurso, sin importar quién lo creó.

#### Conceptos clave

- **Policy Definition (Definición de política):** la regla individual (en formato JSON) que describe la condición a evaluar y el efecto a aplicar. Ejemplo: "todos los Storage Accounts deben tener cifrado habilitado".
- **Initiative (Iniciativa) / Policy Set:** una **agrupación de varias políticas** relacionadas que se asignan juntas como un solo objetivo de cumplimiento (ej. una iniciativa de "cumplimiento ISO 27001" que agrupa decenas de políticas).
- **Assignment (Asignación):** aplicar una definición o iniciativa a un **ámbito** específico (Management Group, Suscripción, Resource Group).
- **Effects (Efectos)** — qué ocurre cuando se evalúa una política:
  - **Deny:** bloquea la creación/modificación del recurso si no cumple la regla.
  - **Audit:** permite la acción pero la marca como "no conforme" en un reporte (no bloquea).
  - **Append:** agrega automáticamente un campo/propiedad al recurso (ej. una etiqueta) antes de crearlo.
  - **Modify:** puede agregar, actualizar o eliminar propiedades de un recurso existente o en creación.
  - **DeployIfNotExists:** si el recurso no cumple, despliega automáticamente un recurso o configuración adicional para corregirlo (ej. habilitar diagnóstico si no existe).
  - **Disabled:** la política existe pero no se evalúa.

#### Ejemplos típicos de uso (frecuentes en preguntas de examen)

- Exigir que todo recurso tenga la etiqueta `CostCenter` o `Environment`.
- Restringir el despliegue de recursos solo a ciertas regiones (ej. `East US`, `West Europe`).
- Permitir solo ciertos SKU/tamaños de VM (para controlar costos).
- Exigir cifrado en reposo en cuentas de almacenamiento.
- Auditar (sin bloquear) recursos que no tengan Managed Identity habilitada.

## 4. Cuadro resumen para memorizar (alto valor en examen)

| Concepto | Definición corta |
|---|---|
| **Resource Group** | Contenedor lógico que agrupa recursos para administrarlos, monitorearlos y facturarlos como unidad. |
| **Management Group** | Agrupa múltiples suscripciones bajo una jerarquía común de gobernanza. |
| **Subscription** | Límite de facturación y de cuotas técnicas; contiene Resource Groups. |
| **RBAC** | Controla **quién** (identidad) puede hacer **qué acción** sobre un ámbito, mediante rol + principal + scope. |
| **Role Assignment** | La combinación de Security Principal + Role Definition + Scope. |
| **Service Principal** | Identidad de seguridad para aplicaciones/automatización (CI/CD) — no es una persona. |
| **Managed Identity** | Identidad administrada automáticamente por Azure AD, asociada a un recurso, sin secretos manuales en código. |
| **Least Privilege** | Otorgar solo los permisos mínimos necesarios, en el ámbito más reducido posible. |
| **Azure Policy** | Controla **qué configuración** es válida para un recurso, sin importar quién lo creó (compliance/gobernanza). |
| **Initiative** | Conjunto de varias Policy Definitions agrupadas y asignadas juntas. |
| **Resource Lock** | `CanNotDelete` o `ReadOnly`, aplicable a RG o recurso, previene borrado/modificación accidental. |

## 5. Autoevaluación — Preguntas del Balotario cubiertas por este tema

Estas son las preguntas del balotario que corresponden directamente al punto 1.1 (más algunas de identidad/gobernanza estrechamente relacionadas), con la explicación de por qué la respuesta correcta lo es:

**b1 — ¿Qué es un Resource Group en Azure?**
✅ *Un contenedor lógico que agrupa recursos relacionados de Azure para administrarlos, monitorearlos y facturarlos juntos.*
Es la definición textual del concepto — memorízala tal cual.

**b6 — ¿Qué es Azure Active Directory (Microsoft Entra ID)?**
✅ *El servicio de identidad y control de acceso de Azure, usado para autenticación y autorización de usuarios y aplicaciones.*
Es el servicio que provee las identidades (usuarios, grupos, service principals) que luego se usan como Security Principal en RBAC.

**b7 — ¿Qué es RBAC (Role-Based Access Control) en Azure?**
✅ *Un sistema que otorga permisos a usuarios, grupos o aplicaciones mediante roles asignados sobre un ámbito (recurso, grupo de recursos o suscripción).*
Ojo con distractores que mencionan "protocolo de red" o "función exclusiva de Databricks" — son incorrectos, RBAC es transversal a todo Azure.

**i12 — ¿Para qué se usan las Azure Policy en una organización?**
✅ *Para aplicar y hacer cumplir reglas de gobernanza sobre los recursos (por ejemplo, exigir etiquetas, restringir regiones o tipos de SKU permitidos).*
El distractor "administrar exclusivamente permisos RBAC" es la trampa más común — Azure Policy **no** es RBAC.

**i13 — ¿Qué diferencia hay entre autenticación y autorización en el contexto de Azure AD?**
✅ *Autenticación verifica la identidad del usuario (quién eres); autorización determina qué acciones o recursos puede acceder ese usuario ya autenticado (qué puedes hacer).*

**i14 — ¿Qué es un Service Principal en Azure AD?**
✅ *Una identidad de seguridad usada por aplicaciones, servicios o herramientas de automatización (como pipelines CI/CD) para autenticarse y acceder a recursos de Azure.*

**a19 — ¿Qué es el principio de 'least privilege' aplicado al diseño de roles RBAC?**
✅ *Otorgar a cada identidad únicamente los permisos estrictamente necesarios para realizar su función, en el ámbito más reducido posible, reduciendo la superficie de riesgo.*

## 6. Tips finales para el examen sobre este punto

1. Si la pregunta menciona **"contenedor lógico" + "facturación/administración conjunta"** → es **Resource Group**.
2. Si menciona **"quién puede hacer qué"**, **"roles"**, **"permisos"**, **"scope"** → es **RBAC**.
3. Si menciona **"reglas"**, **"cumplimiento"**, **"etiquetas obligatorias"**, **"regiones permitidas"**, **"SKU permitidos"** → es **Azure Policy**.
4. Si menciona **"aplicación/pipeline que se autentica sin usuario humano"** → **Service Principal** o **Managed Identity** (esta última sin secretos manuales).
5. Recuerda el orden de la jerarquía: **Management Group → Subscription → Resource Group → Resource**, y que los permisos/políticas se heredan **hacia abajo**.
6. No confundas **RBAC** (personas/identidades) con **Azure Policy** (configuración de recursos) — es el distractor más repetido en el balotario.
