## 1. Azure Functions

### 1.1 Definición

**Azure Functions** es el **modelo de ejecución orientada a eventos (event-driven)** de Azure, donde el desarrollador **despliega pequeñas piezas de código** (funciones) que se ejecutan en respuesta a un evento, **sin aprovisionar ni administrar servidores subyacentes**. Es el servicio de cómputo **serverless** por excelencia de Azure.

> **Definición para examen (memorizar):** *"Un servicio de cómputo serverless que ejecuta pequeñas piezas de código en respuesta a eventos, sin administrar servidores."*

### 1.2 Qué significa "serverless" (sin servidores)

"Serverless" **no significa que no existan servidores físicos** — significa que el **desarrollador no los aprovisiona ni administra**. Azure se encarga de:

- Proveer y mantener la infraestructura de cómputo.
- Escalar automáticamente el número de instancias según la carga (incluyendo **escalar a cero** cuando no hay eventos que procesar).
- Aplicar parches y mantenimiento del entorno de ejecución.

El desarrollador solo se preocupa de **escribir el código de la función** y **definir qué evento la dispara**.

### 1.3 Modelo orientado a eventos (Event-Driven)

Una **Azure Function** se ejecuta en respuesta a un **trigger (disparador)**. Ejemplos típicos de triggers:

- **HTTP Trigger:** la función se ejecuta al recibir una solicitud HTTP (útil para exponer una API ligera).
- **Timer Trigger:** la función se ejecuta según un horario programado (ej. cada noche a la 1 a.m., similar a un cron job).
- **Blob Trigger:** la función se ejecuta cuando se sube o modifica un archivo en Azure Blob Storage / ADLS.
- **Queue Trigger:** la función se ejecuta cuando llega un mensaje a una cola (Azure Queue Storage o Service Bus).
- **Event Hub Trigger:** la función se ejecuta al llegar un evento a un Event Hub (streaming de datos).

Este modelo es muy común en arquitecturas de **ingesta y procesamiento de datos**: por ejemplo, una función que se dispara automáticamente cada vez que llega un nuevo archivo a un Data Lake, para validarlo o iniciar un pipeline de transformación.

### 1.4 Planes de hosting de Azure Functions

El comportamiento de escalado y el costo de una Function dependen del **plan de hosting** elegido:

| Plan | Comportamiento | Relación con el Cold Start |
|---|---|---|
| **Consumption Plan (Plan de Consumo)** | Pago estrictamente por ejecución; escala automáticamente **incluyendo escalar a cero** cuando no hay actividad | **Sufre Cold Start** — es el plan donde ocurre el problema descrito en este punto |
| **Premium Plan** | Mantiene **instancias pre-calentadas (always ready)**, con más control de escalado y redes (VNet integration) | **Elimina/reduce el Cold Start** |
| **App Service Plan (Dedicated)** | La función corre sobre instancias de App Service ya aprovisionadas y dedicadas (no escala a cero por defecto) | **Elimina el Cold Start**, porque las instancias ya están corriendo permanentemente |

## 2. El problema del 'Cold Start' (Arranque en frío)

### 2.1 Definición

El **Cold Start** es la **latencia inicial** que sufre una función bajo el **Consumption Plan** al "despertarse" **tras un periodo de inactividad**. Ocurre porque, al escalar a cero, Azure necesita **aprovisionar una nueva instancia de cómputo** y **cargar el runtime y el código** antes de poder ejecutar la función, lo cual toma un tiempo adicional perceptible en la primera solicitud.

> **Definición para examen (memorizar):** *"La latencia inicial que sufre una función bajo el plan de consumo (Consumption Plan) al despertarse tras un periodo de inactividad."*

### 2.2 Por qué ocurre específicamente en el Consumption Plan

El Consumption Plan está diseñado para **minimizar costos**: si la función no recibe eventos, Azure **libera por completo los recursos de cómputo asignados** (escala a cero, sin costo). Esta eficiencia de costo tiene una contrapartida: cuando llega el **primer evento después de la inactividad**, Azure debe:

1. Aprovisionar una nueva instancia de cómputo.
2. Descargar/cargar el código y las dependencias de la función.
3. Inicializar el runtime del lenguaje (.NET, Node.js, Python, Java, etc.).
4. Recién entonces, ejecutar la función.

Todo este proceso añade **latencia** a esa primera ejecución — las ejecuciones **subsiguientes** (mientras la instancia siga "caliente") son rápidas, porque la instancia ya está lista.

### 2.3 Impacto práctico del Cold Start

- Puede ir desde **cientos de milisegundos hasta varios segundos**, dependiendo del lenguaje, el tamaño de las dependencias y la complejidad de inicialización del código.
- Es especialmente problemático en escenarios donde se requiere **baja latencia garantizada** en cada solicitud (ej. una API HTTP consumida por un sistema en tiempo real), pero **irrelevante** en escenarios de procesamiento por lotes (batch) donde unos segundos extra no afectan el resultado.

## 3. Mitigación del Cold Start

El temario identifica **dos técnicas principales** para evadir esta latencia:

### 3.1 Cambiar de plan de hosting: Premium Plan o App Service Plan

- **Premium Plan:** mantiene un número configurable de **instancias pre-calentadas ("always ready instances")** que están listas para ejecutar funciones **sin necesidad de arrancar desde cero**, eliminando el Cold Start, además de ofrecer tiempos de ejecución sin límite estricto y conectividad VNet.
- **App Service Plan (Dedicated):** la función corre sobre infraestructura ya aprovisionada de forma **permanente** (no escala a cero salvo que se configure explícitamente), por lo que tampoco sufre Cold Start — a cambio, se paga por la infraestructura esté o no en uso (no es pago estrictamente por ejecución como en Consumption).

> **Definición para examen (memorizar):** *"Usar un plan Premium o App Service Plan con instancias pre-calentadas (always ready instances)... según el caso de uso."*

### 3.2 Pings periódicos (Warm-up pings / Keep-alive)

- Técnica que consiste en **invocar la función periódicamente** (por ejemplo, cada pocos minutos, mediante un Timer Trigger o un servicio externo de monitoreo) **para mantenerla activa en memoria** y evitar que Azure la libere por inactividad bajo el Consumption Plan.
- Es una solución **más económica** que cambiar de plan, pero **menos confiable**: Azure puede reciclar la instancia de todas formas (por actualizaciones de la plataforma, balanceo de carga entre datacenters, etc.), por lo que no elimina el Cold Start al 100%, solo lo **reduce en frecuencia**.

### 3.3 Comparación de estrategias de mitigación

| Estrategia | Elimina el Cold Start | Costo relativo | Cuándo conviene |
|---|---|---|---|
| **Premium Plan** | Sí (instancias always ready) | Más alto que Consumption | Cargas con tráfico constante o que exigen baja latencia garantizada, y que además necesitan VNet integration o ejecución prolongada |
| **App Service Plan (Dedicated)** | Sí (infraestructura ya activa) | Fijo, independiente del uso | Cuando ya se tiene infraestructura App Service dedicada y se quiere aprovecharla para correr funciones sin variabilidad de latencia |
| **Pings periódicos (Consumption)** | Parcialmente (mitiga, no garantiza) | El más bajo (sigue siendo pago por consumo) | Cargas esporádicas donde se busca reducir el Cold Start sin asumir el costo fijo de Premium/Dedicated |

> **Idea clave para el examen:** *no existe una única respuesta correcta universal* — la elección depende del **caso de uso**: tráfico constante y baja latencia exigida → Premium/Dedicated; tráfico esporádico y sensibilidad moderada a la latencia → pings periódicos como paliativo dentro del Consumption Plan.

## 4. Cuadro resumen para memorizar (alto valor en examen)

| Concepto | Definición corta |
|---|---|
| **Azure Functions** | Cómputo serverless orientado a eventos; ejecuta código sin aprovisionar ni administrar servidores. |
| **Trigger** | El evento que dispara la ejecución de una función (HTTP, Timer, Blob, Queue, Event Hub, etc.). |
| **Consumption Plan** | Pago por ejecución, escala a cero — plan donde ocurre el Cold Start. |
| **Cold Start** | Latencia inicial al "despertar" una función tras inactividad en el Consumption Plan. |
| **Premium Plan** | Instancias pre-calentadas ("always ready") que eliminan el Cold Start, con más capacidades de red. |
| **App Service Plan (Dedicated)** | Infraestructura permanente dedicada; no escala a cero, sin Cold Start. |
| **Pings periódicos (warm-up)** | Invocaciones programadas para mantener la función activa en memoria y mitigar (no eliminar del todo) el Cold Start dentro del Consumption Plan. |

## 6. Tips finales para el examen sobre este punto

1. Si la pregunta menciona **"sin aprovisionar ni administrar servidores"** + **"en respuesta a eventos"** → es **Azure Functions**.
2. Si la pregunta menciona **"latencia al despertar tras inactividad"** → es **Cold Start**, y ocurre específicamente en el **Consumption Plan**.
3. Recuerda que el Cold Start es consecuencia directa de que el Consumption Plan **escale a cero** — es el "precio" de pagar solo por ejecución.
4. Las dos mitigaciones que el temario exige conocer: **(1)** cambiar a **Premium** o **App Service Plan** (instancias *always ready*), **(2)** **pings periódicos** para mantener la función activa dentro del Consumption Plan.
5. No confundas "eliminar" el Cold Start (Premium/Dedicated) con "mitigarlo parcialmente" (pings periódicos) — el examen puede pedir distinguir cuál técnica es más confiable.
6. Relaciona el **trigger** correcto con el escenario de la pregunta (HTTP, Timer, Blob, Queue, Event Hub) si el enunciado describe un caso de uso concreto.
